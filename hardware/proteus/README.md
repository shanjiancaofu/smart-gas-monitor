# Proteus 仿真说明

本目录用于存放 Proteus 仿真工程（`.pdsprj`）。工程文件需要在 Proteus 里手工搭建，本文给出搭建所需的元件、参数、接线和逐步骤的演示脚本，照着做即可，不需要再推导。

引脚分配以[硬件设计与接线说明](../../docs/hardware_design_and_wiring.md)为准，本文不重复整张引脚表，只写仿真特有的部分。

## 一、仿真能验证什么

**能验证**：采样到执行的完整链路——ADC 读数如何变成状态、状态如何驱动 LED/蜂鸣器/排风扇继电器/舵机阀门、OLED 的各页面、两路串口的命令与应答、报警记录的写入与读回、KEY4 恢复的条件、参数保存，以及掉电后阀门锁存是否真的保留下来（这一条取决于 EEPROM 模型在仿真重启之间是否保留内容，见第七节）。

**不能验证**：MQ 传感器的预热特性与真实响应曲线、继电器接点与实物电平、HC-05 的无线链路、晶振起振、ADC 的噪声特性。这些必须在实物上确认。

## 三、MCU 属性与最小系统

双击 MCU，在属性里设置：

| 属性 | 值 | 说明 |
| --- | --- | --- |
| Program File | `build/keil5/Artifacts/smart_gas_monitor.hex` | Keil 构建的产物，见[固件说明](../../docs/firmware.md) |
| Clock Frequency | **8 MHz** | 必须与固件的 HSE 一致 |

**每次改了固件都要重新编译 Keil 工程，再重新运行仿真**，否则跑的仍是旧 HEX。判断当前跑的是哪一版：仿真日志里会打印 `Loading HEX file ...` 和读入的字节数。

最小系统另外需要：

- **BOOT0 经 10 kΩ 下拉到 GND**，BOOT1 也下拉。BOOT0 悬空时模型可能从系统存储器启动，表现是「下载了固件但什么都不动」。
- 8 MHz 晶体接 PD0/PD1（OSC_IN/OSC_OUT），两端各一个 22 pF 到地。接上更贴近实物；Proteus 的 STM32 模型按属性里的 Clock Frequency 运行，因此即使不画晶体仿真也能跑，但**原理图必须画**。
- NRST 经 10 kΩ 上拉到 3.3 V，并接一个按键到地，方便手动复位重做演示。
- **PA8 经 10 kΩ 下拉到 GND。** 这不是仿真需要，是原理图要求：复位后到 `MX_GPIO_Init()` 之间 PA8 是浮空输入，没有这个下拉，继电器在这段窗口里状态不可控。仿真里加上它，顺带验证复位瞬间继电器确实不吸合。

## 四、供电

**整板只需要一路 5 V 电源**，接 MCU 的 VDD 处——但要注意 Proteus 里这样画只是示意图：真实的最小系统板上 5 V 先进板载稳压器（AMS1117-3.3）产生 3.3 V，MCU 自己是 3.3 V 器件。

**STM32F103 的 VDD 绝对最大额定值是 4.0 V，接 5 V 会烧芯片。** 仿真里模型可能照跑，那是行为级模型的假象，别照着接实物。

| 电源域 | 器件 |
| --- | --- |
| **3.3 V** | MCU、OLED、24C64、蜂鸣器模块、LED |
| **5 V** | MQ 加热器、继电器模块 DC+、HC-05 |

**I2C 上拉必须上拉到 3.3 V，不能上拉到 5 V**——MCU 是 3.3 V 器件，总线拉到 5 V 会超出输入范围。所有器件必须共地。

## 五、三路 "MQ" 怎么模拟

Proteus 没有 MQ-4/6/7 模型。用**电位器模拟 MQ 模块的 AO 输出**，**并保留原理图里真实的 10 k/18 k 分压**——这样仿真接法和最终原理图一致，分压取值也顺便被验证了一次。

每路接法（MQ-4 为例，另两路相同）：

```text
5V ──┬── POT (1k) 两端接 5V 与 GND，中间抽头就是 MQ AO
     │
   抽头 ── R1=10k ──┬──── PA0
                    │
                  R2=18k
                    │
                   GND
```

电位器建议用 **1 kΩ** 而不是 10 kΩ：分压网络的等效负载约 28 kΩ，1 kΩ 电位器在中间位置时源阻抗只有 250 Ω，分压误差小于 1%；用 10 kΩ 时误差接近 8%，演示电压会对不上表。

> 如果你的电位器是**直接接到 ADC 引脚**、没有那个 18 kΩ 下拉，那么下面的电压表要按实际分压比重算。本文按原理图的 10 k/18 k 写。

### 电压与 ADC 读数的换算

固件是 12 位、右对齐，VREF 取 VDDA = 3.3 V，所以：

```text
ADC 计数 = V(AO) × 18/28 × 4095 / 3.3 ≈ V(AO) × 798
```

三路阈值现已统一为 **2400**，所以三路共用同一张表：

| 目标 | ADC 计数 | 抽头电压 V(AO) | 分压后 V(PA0) |
| --- | --- | --- | --- |
| 洁净空气基准 | 约 640 | 0.80 V | 0.51 V |
| 安全线（阈值的 70%） | 1680 | 2.11 V | 1.35 V |
| 预警线（阈值的 80%） | 1920 | 2.41 V | 1.55 V |
| 报警阈值 | 2400 | 3.01 V | 1.93 V |

演示时按这张表拧电位器即可，不必去猜计数。640 那个基准值对应「洁净空气」，低于任何阈值，是演示的起点。

## 六、两路串口怎么连

Proteus 没有 HC-05 模型。两路都用虚拟终端代替，**它就是手机或电脑那一侧**：

| 固件 | Proteus 接法 | 终端设置 |
| --- | --- | --- |
| USART1（USB-TTL） | PA9 → 终端 RXD，PA10 → 终端 TXD | 115200, 8-N-1 |
| USART2（HC-05） | PA2 → 终端 RXD，PA3 → 终端 TXD | **9600**, 8-N-1 |

**串口 2 的波特率必须是 9600**，与固件里 HC-05 的配置一致；设成 115200 会满屏乱码，那不是固件的 bug。

两个终端收到的是同一份内容——同一套文本协议，任一路能做的事另一路也能做。想模拟真实的上位机，可以把 USART1 换成一个 `COMPIM` 绑到电脑的 COM 口，用串口助手当上位机。

## 七、接线要点与常见坑

- **I2C 必须加上拉。** 两组 I2C 各需要在 SDA、SCL 上接 4.7 kΩ 到 3.3 V（**PB6/PB7** 一组，PB10/PB11 一组）。HAL 的 I2C 是开漏输出，没有上拉时总线永远拉不高，表现是「OLED 全黑、EEPROM 读写全失败」。真实的 OLED 和 24C64 模块板上自带这两个电阻，Proteus 里用的是裸芯片，所以要自己加。
- **OLED 接在 PB6/PB7 上。** 这是 I2C1 的**默认**引脚，固件里没有开 AFIO 重映射。这个选择是有原因的：Proteus 的 STM32 模型不认 I2C1 的引脚重映射，一旦开了重映射，仿真里 I2C1 仍停在默认引脚上，挂在重映射引脚的面板一个字节都收不到。早期版本用的是 PB8/PB9 加重映射，在实物上没问题，在仿真里全黑。
- **OLED 未必有模型。** 部分 Proteus 版本带 SSD1306 模型，部分没有。如果搜不到，挂一个 `I2C DEBUGGER` 在 PB6/PB7 上，能看到固件周期性向地址 **0x3C** 写命令和数据——这足以证明面板在被打驱动，但看不到画面。面板的实际显示效果要留到实物确认。
- **面板全黑不等于固件没跑。** `display_update()` 在 OLED 没就绪时直接返回，其余功能不受影响。判断固件是否在跑，看串口有没有应答，而不是看屏幕。
- **蜂鸣器的有效电平必须与固件一致。** 固件里由 `bsp/bsp_buzzer.h` 的 `BUZZER_ON_LEVEL` 决定：
  - 实物用的是**低电平触发**的蜂鸣器模块，`BUZZER_ON_LEVEL = GPIO_PIN_RESET`。
  - 如果仿真里用 NPN 三极管驱动（`PA7 ─ 1k ─ 基极`，发射极接地，蜂鸣器接集电极），那是**高电平触发**，跟当前固件相反，会表现为「待机时一直响、报警时反而不响」。
  - 当前两边**已经一致**：仿真用 PNP（发射极接 VCC、集电极接蜂鸣器、基极经 1 kΩ 到 PA7、10 kΩ 上拉到 VCC），实物用低电平触发模块，都对应 `BUZZER_ON_LEVEL = GPIO_PIN_RESET`。
- **舵机接 PB8，不要外加驱动。** 信号线直连 PB8，舵机电源按它自己的规格单独供（小舵机 5 V，**不要从 STM32 的 3.3 V 取**，堵转电流会把 MCU 拉复位，和舵机共地）。`MX_TIM4_Init()` 已经把 CCR3 预置成 1 ms，所以 PWM 一启动就是关阀位置，不会乱甩。**1 ms 究竟是不是「关」取决于舵机臂的装配**，实物上要按实际行程校准 `bsp_servo.c` 里的两个宏。
- **继电器在 PA8，驱动的是排风扇，不是阀门。** 阀门由 PB8 的舵机控制。报警时两个一起动：继电器吸合开风扇排风，舵机关阀断气。别把这两个看成一个东西——面板上的 `VALVE OPEN/CLOSED` 说的是舵机，不是继电器的状态。
- **配置格式的版本。** 当前是 **v6**。旧版本的记录会被判为无效，整份配置连同阈值和采样周期一起回落到默认值——这是有意的，新版固件不该照着一个旧布局去猜。所以升级固件之后第一次上电时，`CONFIG?` 显示默认值是正常的，不是没存住。
- **存储的掉电保持。** Proteus 的存储模型在仿真运行期间保存内容，但停止仿真再启动是否保留，取决于版本和模型属性。这一条很重要：阀门锁存和阈值都寄存在这片存储里（配置区 0x00～0x1F，第 12 字节是 lockout 标志）。**如果模型重启后回到全 1**，那么每次上电都被当作干净上电，第 2 步的自动开阀和后面的锁存演示都会变成「回到了初始状态」——这不是固件的 bug，是模型没掉电保持。做法是先实测：改一个阈值、停止仿真、重新运行，用 `CONFIG?` 看阈值还在不在。在不在，锁存演示才有意义；不在，锁存这一条只能留到实物确认。
- **ADC 是第一个要确认的环节。** 如果上电后 OLED 直接显示 `FAULT`，通常是 Proteus 的 ADC 模型没有按预期完成转换。固件用 `HAL_ADC_PollForConversion(..., 5)` 轮询，5 ms 内没完成就判为采样失败。遇到这种情况先确认 Clock Frequency 是 8 MHz，再检查 PA0/PA1/PA4 上确实有电压。
- **???????? `1=ALWAYS`**??? ALARM/FAULT ?????????????`0=OFF`?`1=ALWAYS`?`2?60=????`?
- **预热只有 3 秒。** 真实 MQ 传感器要热机几分钟以上，本项目按演示需要固定取 3 秒。预热期间阀门保持关闭、不判气体阈值，但 ADC 或采样链路真失败仍会进 `FAULT`。

## 八、演示脚本

每一步都给出预期现象，对不上就查第九节。**三路电位器初始都调到 0.80 V 左右（约 640 计数）。**

### 1. 上电与预热

运行仿真。预期：

- OLED 实时页三行显示 `MQ4   640/2400`、`MQ6   640/2400`、`MQ7   640/2400`，末行 `WARMUP  CLOSED`
- 黄灯灭，绿灯灭，红灯灭，阀门指示灯灭
- 舵机收到关闭脉宽（PB8，1 ms）
- 风扇继电器不吸合（PA8 为低），触点侧的小电机不转
- 蜂鸣器不响
- 两个虚拟终端都没有输出

预热是 3 秒**仿真时间**。Proteus 仿真 72 MHz 的 STM32 一般慢于实时，实际等待可能长一些，取决于机器和版本。

### 2. 预热结束，自动开阀

预期：状态变成 `NORMAL  OPEN`；绿灯亮；阀门指示灯亮；舵机转到打开脉宽（PB8，2 ms）。
**风扇仍然不转**——NORMAL 不需要排风，PA8 保持低。**这一步不需要按任何键。**

这条成立的前提是存储里没有留存上一次的锁存（配置区第 12 字节为 0）。如果是第一次运行、或者上一轮结束时阀门是开着的，就会看到这个现象；如果上一轮是带着报警或远程关阀结束的，存储里留着锁存，那么预热结束后不会自动开阀——那是对的，见第 9 步。

在任一终端输入 `STATUS?`（终端里直接敲，回车）：

```text
STATE=NORMAL VALVE=OPEN ALARMS=0
MQ4=640/2400 MQ6=640/2400 MQ7=640/2400
```

### 3. 预警

把 MQ-4 那一路的电位器调到 **2.41 V**（约 1920 计数）。预期：

- OLED 末行 `WARNING OPEN`，`MQ4 19xx/2400`
- 黄灯亮，绿灯灭，红灯灭
- **阀门保持打开**，舵机不动；风扇也不转
- 蜂鸣器不响，串口不主动推送

### 4. 报警

把 MQ-4 电位器调到 **3.01 V**（约 2400 计数）以上。预期：

- OLED 末行 `ALARM  CLOSED`，`MQ4 24xx/2400`
- 红灯亮，黄灯灭，绿灯灭
- **舵机立即转到关闭脉宽，阀门关闭**，阀门指示灯灭
- **风扇继电器吸合（PA8 变高），小电机转起来排风**
- ?????????**?? 1=ALWAYS???????**??????????????????
- 参数页的 `ALARMS` 计数加一

两个终端同时自动打印一行，不需要查询：

```text
ALARM MQ4 MQ4=24xx MQ6=640 MQ7=640
```

报警持续期间记录**只写一条**。把电位器继续往上拧，不会再产生新记录。

### 5. 查历史

任一终端输入 `HISTORY?`：

```text
HISTORY 1/510
1 SEQ=1 MQ4=24xx MQ6=640 MQ7=640 ALARM=MQ4 UP=6
```

`UP` 是报警发生时设备已运行的秒数。**没有日期时间**——板上没有 RTC，记录里存的是它确实知道的那个量，而不是伪造一个时间戳。

也可以按 KEY1 切到历史页，OLED 上看到同样的内容：`HIST 1/1`、`SEQ 1 UP6s`、`MQ4 24xx MQ6 640`、`MQ7 640 A1`。历史页上 KEY2/KEY3 是翻阅记录，不是改参数。

### 6. 浓度恢复，阀门保持关闭

把 MQ-4 电位器拧回 0.80 V（约 640 计数）。预期：

- 状态变成 `SAFE`（已恢复，等待确认）
- 红灯灭，黄灯亮，绿灯灭
- **阀门仍然关闭**，舵机保持关闭脉宽；**风扇继续转**——气体散了但锁存还没解除，排风不停止

这一步是整个设计的重点：气体散了不等于可以重新开阀，必须人工确认。

### 7. KEY4 恢复

三路都低于安全线并**持续 3 秒**后，按 KEY4。预期：

- 状态回到 `NORMAL`，舵机转回打开脉宽，阀门重新打开，绿灯亮，黄灯灭
- **风扇停转**（PA8 变低）
- 参数页 `ALARMS` 计数不变

**反向也要试一次**：再走一遍第 4 步制造报警，第 6 步把浓度调低，然后在 3 秒之内按 KEY4——应该**没有反应**。恢复条件不满足时按键必须无效，这是被主机测试覆盖的行为。

### 8. 远程关阀，以及为什么不能远程开阀

任一终端输入：

```text
VALVE CLOSE      →  OK VALVE=CLOSED
VALVE OPEN       →  ERR ONLY CLOSE
```

`VALVE CLOSE` 会让阀门关闭并锁存；`VALVE OPEN` 被明确拒绝。这是设计要求：如果链路上能开阀，锁存就形同虚设。远程关阀之后要想开阀，走的是和第 7 步完全一样的路——三路低于安全线持续 3 秒，然后按 KEY4。

关阀之后 OLED 会显示 `SAFE  CLOSED`、黄灯亮，这是正常的：软件只知道阀门被锁存了，而它同时知道当前浓度是安全的，两个事实分别显示，谁也不掩盖谁。

### 9. 掉电之后阀门仍然锁着

接第 8 步（阀门处于锁存状态），停止仿真再重新运行。**先确认第七节的存储掉电保持这一条已经实测过。**

预期：

- 上电不自动开阀。预热 3 秒内显示 `WARMUP  CLOSED`，预热结束后进入 `SAFE  CLOSED`——阀门**始终关闭**
- **风扇从上电起就在转**——`lockout` 从存储里恢复为 1，预热期间也保持排风，这是设计要求的
- 阀门指示灯灭，黄灯亮，绿灯灭
- 三路电位器都在 0.80 V（浓度是安全的），阀门照样不开
- 串口：

```text
STATUS?
STATE=SAFE VALVE=CLOSED ALARMS=1
MQ4=640/2400 MQ6=640/2400 MQ7=640/2400
```

三路都低于安全线并持续 3 秒后按 KEY4，阀门才重新打开。这一条是整个系统里最值得演示的：气体散了、电也断过了，阀门还是关着——因为它关阀的理由不因为断电而消失。

**对照实验**：把存储里的 lockout 清掉（按 KEY4 开阀，或换一片空的存储模型）之后重新运行，同样的浓度下应该在预热结束时自动开阀。两次的差别就是那一个字节。

### 10. 在线改参数

按 KEY1 切到参数页，OLED 显示：

```text
SETTINGS
>MQ4 2400
 MQ6 2400
 MQ7 2400
 PERIOD 100MS
 BUZZER ALWAYS
```

参数页用小号字体，一屏放得下全部 5 个可调项。**按 KEY5 逐项切换**（MQ4 → MQ6 → MQ7 → PERIOD → BUZZER → 回到 MQ4），`>` 标出当前项；KEY2/KEY3 改值。停手 2 秒后自动保存。

用 KEY2 把 MQ4 阈值改到 2500，任一终端输入 `CONFIG?` 确认：

```text
TH MQ4=2500 MQ6=2400 MQ7=2400 PERIOD=100 BUZZ=ALWAYS
```

串口改参数走的是同一条校验路径，可以对照测试：

```text
SET MQ4 2600      →  OK MQ4=2600
SET PERIOD 500    →  OK PERIOD=500
SET PERIOD 255    →  ERR RANGE      （不是 10 ms 的整数倍）
SET MQ4 100       →  ERR RANGE      （低于下限 200）
SET MQ4 abc       →  ERR VALUE
SET MQ9 1000      →  ERR NAME
NONSENSE          →  ERR UNKNOWN
```

### 11. 长报文不打断采样

输入 `HISTORY?`，或在终端里连续敲几条命令。预期：

- 应答逐行出现，不会卡住
- **全程不出现 `FAULT`，阀门不会因为查询而关闭**

这一条是特意设计并验证过的：510 条记录在 9600 baud 下要发很久，比采样器自己的故障超时（100 ms 周期下只有 300 ms）长得多。所以应答是中断发送、每次主循环只发一行。如果演示时发现查询命令会把阀门关掉，说明这一层坏了。

## 九、故障排查

| 现象 | 先查什么 |
| --- | --- |
| 什么都不动，终端无应答 | BOOT0 是否下拉；Clock Frequency 是否为 8 MHz；HEX 路径是否正确、**改完固件有没有重新编译 Keil** |
| 上电直接 `FAULT` | ADC 模型是否完成转换；PA0/PA1/PA4 上是否有电压；Clock Frequency |
| **OLED 全黑** | I2C 上拉是否加了；**OLED 是否接在 PB6/PB7**（不是 PB8/PB9）；挂 `I2C DEBUGGER` 看总线上有没有向 0x3C 写数据；也见第七节 |
| **蜂鸣器一直响** | 先看档位：设成 `ALWAYS` 就一直响到报警解除，那是设置不是故障。若待机就响，查极性——固件按低电平触发写（`BUZZER_ON_LEVEL = GPIO_PIN_RESET`），仿真和实物都应按此接（PNP 或低电平触发模块，见第七节），装成 NPN 就会反过来 |
| 参数存不住 | I2C2 上拉是否加了；24C64 模型的地址是否为 0x50 |
| 串口 2 乱码 | 终端波特率是否设成 **9600** |
| 串口 1 乱码 | 终端波特率是否设成 **115200** |
| 按键按了没反应 | 按键一端是否接 GPIO、另一端接地；GPIO 是否配了内部上拉（由固件的 `MX_GPIO_Init` 负责，不要额外加上拉） |
| 风扇在复位瞬间转动 | PA8 的 10 kΩ 下拉是否加了 |
| **报警时风扇不转** | 继电器是否接在 **PA8**（不是 PA5——PA5 是阀门指示灯）；PA8 报警时应为高 |
| **舵机不动或乱甩** | 信号线是否接 **PB8**；PB8 有没有被别的功能占用；舵机电源是否独立供且与 MCU 共地；脉宽方向要不要对调（见第七节） |
| 阀门动作和面板显示相反 | `bsp_servo.c` 里 1 ms/2 ms 哪个是「关」取决于舵机臂装配，按实际行程调换两个宏 |
| 浓度正常但上电不开阀 | 多半是对的：存储里留着上一次的锁存。用 `STATUS?` 看 `VALVE=CLOSED` 且 `STATE=SAFE` 即是此情形，按 KEY4 解除 |
